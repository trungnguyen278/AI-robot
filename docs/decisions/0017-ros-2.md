# 0017 — ROS 2 on the robot: every module a node, the body through ros2_control, on Ubuntu

- **Status:** Proposed
- **Date:** 2026-10-27
- **Supersedes:** [ADR-0005](0005-pi-software-platform.md)

## Context

- [ADR-0005](0005-pi-software-platform.md) chose "no ROS 2 for now", to be revisited when navigation or arm planning starts. That postponed the choice that shapes everything the robot will add, which [design rule 5](../../CONTRIBUTING.md#design-rules) does not allow.
- What the robot will do ([vision](../vision.md)):
  - drive on tracks, avoid obstacles, follow a person;
  - turn its head towards people;
  - gesture with two 3-DOF arms, perhaps pick up light objects;
  - notice people and faces.
- In robotics, ROS 2's ecosystem is the standard way to do these things:
  - ros2_control drives actuators through one hardware interface, with ready-made controllers: differential drive with odometry, joint trajectories, sensor broadcasters;
  - one description of the robot's geometry (URDF) feeds tf, RViz, Gazebo, Nav2 and MoveIt alike;
  - Nav2 and SLAM Toolbox navigate, and MoveIt 2 plans arm motion;
  - REP 155 (ROS4HRI) sets how a robot represents the people it perceives;
  - rosbag records, RViz and Foxglove show, Gazebo simulates.
- ROS 1 ended with Noetic on 31 May 2025. The current ROS 2 LTS is Lyrical Luth, supported from May 2026 to May 2031.
- Where Lyrical runs:
  - Tier 1 on Ubuntu 26.04 (amd64 and arm64) and Windows 11;
  - Tier 3 on Debian Trixie, the base of Raspberry Pi OS: built from source, and supported only until 2028-08-09;
  - ROS 2's guide gives two ways on a Raspberry Pi: Ubuntu with the binary packages, or Raspberry Pi OS with ROS 2 in Docker.
- Ubuntu 26.04 LTS was released in April 2026 and is supported to April 2031. Canonical certifies it on the Raspberry Pi 5.
- Checked on 2026-10-27 in the official `ros:lyrical-ros-base` image (Ubuntu 26.04.1, Python 3.14.4):
  - every package this decision relies on is released for Lyrical: ros2_control and its controllers (differential drive, joint trajectory, range, battery, GPIO), Nav2, SLAM Toolbox, MoveIt, hri_msgs, camera_ros, gz_ros2_control and foxglove_bridge;
  - rclpy has an asyncio-native node, `AsyncNode`, still in `rclpy.experimental`;
  - today's software passes all 527 of its tests on Python 3.14, after one fix;
  - NetworkManager 1.54 and BlueZ 5.85 keep the polkit and D-Bus policies the set-up adapters rely on;
  - PortAudio initializes only when a PulseAudio-compatible server answers, such as PipeWire;
  - importing ROS's `launch` package changes Python's logger class, which breaks tests that capture logs when its pytest plugins load.
- Measured on the robot's Raspberry Pi 5 on 2026-10-28, under Raspberry Pi OS, with ROS 2 in Docker:
  - today's software passes all 527 of its tests there, the C++ extension included. Running, it takes 54 MB of memory (PSS) and 0.25 % of one core;
  - **CPU:** nine Python nodes in a ring, each publishing ten messages a second:
    - nine processes with rclpy's `Node`: 13.6 % of one core;
    - nine processes with `AsyncNode`: 5.5 %;
    - nine nodes in one process, on rclpy's single-threaded executor: 26 %;
  - **memory:** each Python node's process takes about 170 MB. 128 MB of it is one region that LTTng-UST, the tracing library that `librcl` loads, makes under the 16 KB memory pages of Raspberry Pi OS's Pi 5 kernel.
    - With 4 KB pages, loading LTTng-UST costs 2 to 5 MB, measured on x86 and in the arm64 image emulated, and `import rclpy` 33 MB on x86.
    - Ubuntu's Raspberry Pi kernel for 26.04 (Linux 7.0) uses 4 KB pages: its configuration turns 16 KB pages off on arm64.
  - That kernel also builds every overlay the robot's hardware needs: the TPM, the Pi 5's UART0 and UART2, SPI0, I2C1, the Waveshare DSI panel and the IMX500.
  - The robot's Pi has a bootloader EEPROM dated 2025-12-08, a version known to boot Ubuntu 26.04.
- The camera on Ubuntu:
  - libcamera and rpicam-apps are in Ubuntu's archive, for every Pi camera;
  - Picamera2 is not in it yet;
  - the IMX500's firmware cannot be: Ubuntu's maintainers say its license does not allow it, and Ubuntu's guide installs it from Raspberry Pi's archive.
- By default, ROS 2 discovers every node on the subnet. On a home network, any device on the Wi-Fi could then see the robot's topics and publish to them.
- How others build:

| Robot | Software |
|---|---|
| Reachy 2 (Pollen Robotics) | ROS 2 inside, with the hardware through ros2_control; a gRPC SDK outside, so that users need no ROS |
| TurtleBot 4 | ROS 2 on Ubuntu, on a Raspberry Pi 4; its iRobot Create 3 base runs ROS 2 itself |
| Stretch (Hello Robot) | Its own Python driver, `stretch_body`, under ROS 2 interfaces |
| Spot (Boston Dynamics), Unitree Go2 | Their own core (gRPC; DDS), with ROS 2 drivers on top |
| Reachy Mini | No ROS: its own daemon, with an HTTP and WebSocket API |

## Decision

1. **ROS 2 is the robot's framework, and its only internal bus.**
   - Every module becomes a ROS 2 node. The robot's software parts talk only through ROS 2 topics, services and actions.
   - The outside world is reached at the edges, each edge owned by one node, through the protocols that already exist: the screen (the renderer's WebSocket), the cloud (LiveKit), set-up (Bluetooth LE), and the body (the body controller's link, through ros2_control).
2. **LTS distributions only, and never ROS 1.** Lyrical Luth now. The robot moves to each next LTS (the next one in May 2028), with the Ubuntu LTS it targets, within a year of its release.
3. **Ubuntu 26.04 LTS Server, 64-bit, on the Pi 5**, with ROS 2 from its official packages. It replaces Raspberry Pi OS.
   - Its kernel uses 4 KB pages, which spares each node's process the 128 MB that LTTng-UST takes under 16 KB pages.
   - **The camera:** libcamera and rpicam-apps come from Ubuntu. The project packages Picamera2 from Raspberry Pi's sources.
   - **The IMX500's firmware:**
     - the robot fetches it from Raspberry Pi's archive during set-up, as Ubuntu's guide does, so the project never redistributes it;
     - it is kept on the data partition, which the kernel searches for firmware;
     - its license is checked before the first robot ships.
   - **The screen:** Ubuntu Frame shows the renderer in Chromium, in kiosk mode. Chromium is the engine the renderer's tests run in.
   - **Sound and networks:** sound goes through PipeWire ([ADR-0013](0013-listening-on-the-robot.md)), started before the nodes that use it. NetworkManager manages networks, as netplan's renderer.
4. **Python nodes on asyncio, C++ where timing matters.**
   - Each module keeps its logic, its ports and its adapters.
   - One node class of ours hosts a module. It is built on `AsyncNode`, which used less than half the CPU of rclpy's `Node` in the measurement above. It is the only code that uses rclpy's node API, so `AsyncNode` leaving `rclpy.experimental` changes one file.
   - C++ (rclcpp) for the ros2_control hardware interface and any controller of our own.
   - The pybind11 extension stays, each function with its Python twin.
5. **Messages are ROS 2 interfaces**, defined once, in the `ai_robot_interfaces` package.
   - Standard interfaces are used wherever one fits: `sensor_msgs/BatteryState`, `geometry_msgs/Twist`, `control_msgs/FollowJointTrajectory`, `hri_msgs`, Nav2's actions.
   - Checks stay with the publisher: the node class runs a message type's checks before it publishes.
6. **Configuration is ROS 2 parameters.**
   - Each node declares its parameters, typed and described, with no default in code.
   - Their values are in YAML files, with a comment for each.
   - Profiles become launch arguments.
   - Values for one machine stay in a git-ignored file, loaded last.
7. **Each node runs in its own process, as a managed (lifecycle) node.**
   - The launch brings the nodes up in order.
   - A node that fails restarts while the others run.
   - Motion stays safe meanwhile, through the controllers' command timeouts and the body controller's watchdog (design rule 4).
8. **The body through ros2_control.**
   - **The description:** the robot's URDF, written with xacro, is the one source of its geometry. It follows REP 103 (units) and REP 105 (frames).
   - **One hardware interface** for the body controller, which speaks the body protocol, defined once in `protocol/body/`.
   - **The controllers:**
     - differential drive for the tracks;
     - joint trajectories for the neck and for each arm;
     - broadcasters for the joints, the distance sensor and the battery;
     - GPIO for the lights.
   - **The body controller** keeps the real-time loops (motor speed, encoders, the servo bus, sensors, lights) and the watchdog. It drives the motor driver from the wheel speeds ros2_control asks for.
     - It runs our protocol, not micro-ROS: ros2_control's boundary is the hardware interface, and a single owner keeps the safety.
   - **Without the body**, the same controllers run on ros2_control's mock hardware or in Gazebo. They replace today's simulated body ports.
   - **The `motion` node** stays the robot's one door to movement. Behaviors and the cloud ask it, and it arbitrates between them, enforces expiry and the safety classes, and commands the controllers.
9. **People follow REP 155 (ROS4HRI).** The vision node publishes faces and bodies, and the voice node publishes voices, so ROS4HRI packages work with the robot as they are.
10. **Navigation is Nav2 with SLAM Toolbox; arm planning is MoveIt 2**, both configured from the description.
    - They need a range sensor (a lidar or a depth camera), and arms that can grasp.
    - Adding them is a hardware decision, then configuration.
11. **The ROS graph never leaves the robot.**
    - It runs on Fast DDS, Lyrical's default middleware, with `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST` for every node.
    - A developer reaches the graph through SSH: the ROS 2 command line on the robot, and foxglove_bridge, started on demand and tunnelled over SSH.
    - The cloud and the app reach the robot only through their protocols, and the cloud only within the safety classes (SEC-8, SEC-9).
12. **Development in a container.**
    - A dev container (`.devcontainer/`, Ubuntu 26.04 with Lyrical) works on Windows, macOS and Linux. RViz and Gazebo run in it, through WSLg on Windows.
    - `software/` becomes a colcon workspace. `colcon test` runs both pytest and the launch tests; the unit tests load neither the `launch_testing` nor the `launch_ros` pytest plugin.
    - CI runs in the same image, on amd64 and on arm64.

## Alternatives considered

| Alternative | Why not |
|---|---|
| No ROS 2, for good | Navigation, arm planning, the robot's description, simulation, recording and the tools would all be ours to build and keep, and nothing from the ecosystem would plug in. |
| Our core, with a ROS 2 bridge at its edge (as Spot or Stretch) | Each kind of data that crosses the bridge needs a mapping on both sides, so most new features touch the core, the bridge and ROS. Tools and recordings see only what is bridged. |
| ROS 2 for motion only, our bus for the rest | Two buses, two configurations and two ways to test, joined by a bridge. Features that cross, such as looking at whoever speaks, touch both sides. |
| Raspberry Pi OS with ROS 2 in Docker | The other way ROS 2's guide gives. But nearly every node needs a device: sound, Bluetooth and NetworkManager over D-Bus, the camera, the TPM, the body's serial port. Each would be passed into the containers, with two systems to keep in step. |
| Raspberry Pi OS with ROS 2 built from source | Tier 3: we would build every package (ros2_control, Nav2, MoveIt), and Lyrical's support for Debian Trixie ends in August 2028. |
| micro-ROS on the body controller | The microcontroller would join the ROS graph. But ros2_control still needs a hardware interface, and the agent and DDS-XRCE would sit inside the control loop. A plain protocol behind the hardware interface is the pattern ros2_control's maintainers describe. |
| Zenoh as the middleware | Tier 1 in Lyrical, and better than DDS across Wi-Fi. But the robot's graph stays on the robot, where DDS discovery costs little, and the discovery range setting keeps it there. With Zenoh, which ignores that setting, it would rest on the router's configuration. |

## Consequences

- Positive:
  - a new sensor, controller or ROS 2 package is configuration and a node, not a rework. Navigation and arm planning plug into what exists;
  - one bus that standard tools see: `ros2 topic`, RViz, Foxglove, and rosbag recording everything the robot does;
  - a node that fails restarts alone;
  - the body is simulated by the same controllers that drive the real one;
  - shared conventions (REP 103, 105 and 155), and skills that carry over to other robots.
- Negative / accepted trade-offs:
  - the runtime is rewritten: the bus, the configuration, the lifecycle, packaging and launch. Modules keep their logic, ports, adapters and tests;
  - development needs the container: the software no longer runs on any computer with Python alone;
  - more memory, with a process and the middleware for each node: roughly 50 MB each with 4 KB pages, an estimate from the measurements above, so about half a gigabyte for nine, against 54 MB for today's whole process. The Pi 5 has 8 GB;
  - the camera's AI depends on Raspberry Pi's archive for its firmware, and we package Picamera2;
  - `AsyncNode` is experimental, so it stays behind our node class;
  - the image changes to Ubuntu 26.04, built with `ubuntu-image` ([ADR-0014](0014-updates.md), revised);
  - PortAudio needs PipeWire running, in CI too.
- Follow-up:
  - measure on the Pi 5 under Ubuntu: memory for each node; and, once the display and the camera are connected, the face's frame rate in Chromium under Ubuntu Frame ([ADR-0006](0006-screen-renderer.md)) and the camera;
  - the body protocol and the body controller ([ADR-0004](0004-pi-software-first.md)), now behind ros2_control;
  - the migration, in the order given in [the architecture](../architecture.md#migration).
