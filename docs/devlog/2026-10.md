## 2026-10-16 — Requirements for the cloud link

**Done:** The core AI will run in the cloud (`ai-robot-server`, to be built anew rather than ported from the previous generation's server), and moods such as sleepiness probably with it. Drafted the requirements of the robot ⇄ cloud link in [`protocol/cloud/requirements.md`](../../protocol/cloud/requirements.md):
- what goes up and down;
- sessions, turns and barge-in;
- media negotiation: one side offers the codecs it supports in order of preference and the other answers, as SIP endpoints such as FreeSWITCH do (RFC 3264), with a baseline format so that it never fails;
- extensibility: the robot declares capabilities with schemas and safety classes, and the cloud calls them through one generic message, MCP-shaped, so that it can drive more of the robot without protocol changes;
- performance, reliability and working offline;
- security, checked against ETSI EN 303 645 and the OWASP IoT Top 10, and privacy;
- set-up, operations and tests.

They draw on the previous generation's protocol, xiaozhi-esp32, MCP, the Gemini Live and OpenAI realtime APIs, and Alexa Voice Service.
**Decisions:** none yet; seven are listed in its §13, each to become an ADR (transport, message format, audio, end of speech, device identity, updates, where moods live).
**Problems / unfinished:** `ai-robot-server` does not exist yet, so the requirements on the server side are for when it does. Children's data policies are to be defined before the first real users.
**Next:** Review the requirements with the user; then the ADRs of §13, starting with the transport and the message format; then a simulated cloud on the robot side (TEST-2).

## 2026-10-17 — The cloud link, version 1.0

**Done:** [Protocol 1.0](../../protocol/cloud/README.md) for the link between the robot and the cloud, with [`schema.json`](../../protocol/cloud/schema.json) and two example sessions that the tests check. On the robot:
- **The `cloud` module and port.** Two adapters: `sim`, a simulated cloud for running without a server and for tests (TEST-2), and `websocket`. The `websocket` adapter:
  - opens one connection and exchanges the hello;
  - acts as an MCP server (`server/discover`, `tools/list`, `tools/call`, `subscriptions/listen`, cancellation);
  - sends events and limits the cloud's message rate;
  - reconnects with backoff and resumes the session.
- **Capabilities.** Modules offer them on the bus with `CapabilityHost`, as EXT-9 asks. The cloud module checks the arguments against the schema, keeps out the safety classes the owner has not allowed, and times out a call that gets no answer.
- **The screen** offers `screen.show_expression`, `screen.set_mood` and `screen.show_scene`, with schemas built from its vocabulary, and the event `screen.touched`.
- **Shared code.** The JSON helpers moved to `core/data.py`, and the software's version to `ai_robot.software_version()`.
- **Checked end to end.** The robot, configured for the `websocket` adapter, worked against a small local cloud: it listed its tools, showed an expression and a scene, refused an unknown expression, and said goodbye when it stopped.

**Decisions:**
- The protocol builds on [ADR-0007](../decisions/0007-cloud-link-transport.md) and [ADR-0008](../decisions/0008-cloud-link-messages.md), still `Proposed`.
- Credentials are a bearer token from `AI_ROBOT_CLOUD_TOKEN`, provisional until decision 5.
- The cloud sees only `informational` capabilities by default.
- Invalid arguments are a tool error rather than a protocol error, as MCP advises; EXT-2 now says so.

**Problems / unfinished:**
- Turns, responses and audio frames are specified but not implemented. They wait for the voice pipeline (wake word, VAD), and until then the robot offers no audio formats.
- Renegotiating media (NEG-4) and announcing events declared after the hello are left to a later minor version.
- The `ai_backend` port of `voice` is to be replaced by turns over the link.

**Next:**
- Turns and audio on the robot, with the voice pipeline.
- More capabilities as modules gain them: gaze, motion (`physical`, off by default), timers on the robot (REL-2).
- The remaining decisions of the requirements: audio, end of speech, device identity, updates, moods.

## 2026-10-22 — The cloud link, version 2.0

**Done:** [Protocol 2.0](../../protocol/cloud/README.md) and its robot side, following ADR-0009.
- **The room.**
  - The robot joins its LiveKit room and says hello to the cloud's agent once it is there.
  - It takes messages and audio only from participants of kind `agent`, which only the server can grant.
  - Only that agent may subscribe to the robot's microphone.
- **Messages.** The session's messages keep the shape of 1.0 (MCP, events, turns and responses), carried as text streams.
  - Too many at once now wait in a backlog instead of being dropped.
  - The robot's `turn.speech_end` says how much speech it sent, since the message and the audio travel apart.
- **Audio.**
  - The user's speech goes out on the robot's `speech` track, muted outside turns.
  - The agent's voice comes back live.
  - Opus and its negotiation come from WebRTC. The PCM baseline, the media offer and the binary frames of 1.0 are gone.
- **Code.** The WebSocket adapter gave way to `adapters/livekit/`.
  - `Session` holds the protocol and knows nothing of LiveKit, so its tests run without a server.
  - `LiveKitCloud` carries it through the room.
  - PR #16's turns and conversation messages were kept, minus its audio frames.
- **Tests.** Most run without a server. Three run against a real LiveKit server when one is found, and the software workflow downloads one, pinned and checked.
- **Checked end to end.** The robot ran with the `livekit` adapter against `livekit-server --dev`, with a script as the agent. It said hello, listed its tools, showed `happy` on request, and said `bye` when it stopped.

**Decisions:** within ADR-0009:
- The agent answers the robot's hello, and never speaks first. This avoids acting on a message from a participant whose kind is not known yet.
- `response.interrupted` no longer carries `played_ms`: on a live track, the agent knows what it sent and when, as OpenAI's WebRTC API does.

**Problems / unfinished:**
- Muting the speech track at once loses what is still queued, which is the end of the user's sentence. The robot now lets it play out first. Found by the tests.
- Tokens come only from a development server's key. The token endpoint comes with ADR-0010.
- Not tried on a Pi yet: the SDK's wheels and CPU load.

**Next:** ADR-0010 on the robot (identity port, TPM, token endpoint), then the voice module.

## 2026-10-22 — The robot's identity

**Done:** [ADR-0010](../decisions/0010-device-identity.md) on the robot, all but the TPM.
- **Protocol 2.1: the token endpoint.**
  - The robot proves who it is with a JWT it signs with ES256: OAuth 2.0 client authentication, RFC 7523.
  - It gets back the LiveKit server's address, a token for its room, and a token for the server's API.
- **An `identity` port.** The `cloud` module owns it and hands it to the link. Two adapters:
  - `sim`: a new key at each start;
  - `file`: a key kept in a file, for a development computer.
- **The `livekit` adapter** gets its tokens from the server (`tokens = "server"`), or still makes them for a development server (`"development"`).
- **Tests.**
  - A fake token endpoint checks the robot's assertions with PyJWT, a library of its own, which proves the hand-made JWTs standard.
  - A robot gets its room from that endpoint and joins a real LiveKit server.
- **A security review** found no vulnerability, and two hardenings came of it:
  - the robot does not follow a redirect from the token endpoint, which would carry its assertion elsewhere;
  - the `file` adapter refuses a key file that others can open, as SSH does.
- **A flaky test** showed that LiveKit's SDK sends each change of permissions from a task of its own, so two changes close together may reach the server in either order: an agent already in the room could be shut out of the robot's microphone. The robot now denies everyone before it publishes its track, and sends the latest permissions once more half a second after a change.

**Decisions:** within ADR-0010:
- The endpoint is `/robot/token` on the server.
- An assertion's `kid` is the key's JWK thumbprint, so that a robot can change keys.
- The identifier is a random UUID, kept with the key.

**Problems / unfinished:**
- The TPM: a hardware change, then its adapter, tested against a software TPM.
- Nothing registers a robot's key with a server yet: that comes with set-up, on the touch screen and in the app.
- The LiveKit server of the tests failed to start in 2 of 25 local runs, for a reason not found; it now reports what it said when that happens.

**Next:** The TPM (the hardware change, then its adapter), then the voice module.

## 2026-10-23 — The robot's ears, and its TPM

**Done:**
- **The TPM's place on the header.** An SPI TPM, the LetsTrust (SLB 9672, SPI0 with CE1, reset on GPIO24), clashed with the ReSpeaker HAT. The HAT's APA102 LEDs listen on SPI0's data and clock without a chip select, and the HAT covers pins 17 to 26. The I2C alternative, Infineon's SLB 9673 board, is a second full HAT whose overlay forces software I2C.
- **So the audio, never settled, came first.** [ADR-0011](../decisions/0011-audio-voice-processor.md), proposed: the robot hears through a USB voice processor, the XMOS XVF3800 4-microphone array, as Reachy Mini does, and speaks through it, so that its echo canceller has the reference.
- **The hardware docs follow the proposal.**
  - Into the BOM, as proposed: the XVF3800, a 5 W speaker and the TPM. Out: the HAT and the MAX98357A.
  - The header carries no audio.
  - Three new open issues: the array's power, where it sits, and parts on the header against the chassis' vibration.
- **The `tpm` adapter of the `identity` port.**
  - The key is a primary key that the TPM derives from its owner seed with a fixed template, P-256 and bound to the TPM.
  - The identifier sits in an NV index, written once and then locked. Clearing the TPM gives a new identity.
  - tpm2-pytss comes as the `tpm` extra, and the pi profile selects the adapter.
- **Tests** run against swtpm, which CI installs with libtss2-dev. An adapter whose library is not installed is now a configuration error.

**Decisions:**
- [ADR-0011](../decisions/0011-audio-voice-processor.md), proposed.
- Within ADR-0010: the key is derived from the seed rather than kept in a persistent slot, and the identifier lives in the TPM's NV memory.

**Problems / unfinished:**
- ADR-0011 awaits agreement; the hardware docs assume it.
- On the XVF3800 board, still to check: its current at the robot's volume, whether its mute cuts the microphones, and the speaker's connector.
- Nothing has run on a Pi with a real TPM: the adapter was developed against swtpm, in containers of Debian "Trixie" and Ubuntu 24.04.

**Next:** After review, the voice module: wake word, voice activity, playback through the array. Then the set-up protocol, which registers the robot's key.

## 2026-10-24 — The robot listens

**Done:**
- **Decision 4, the end of speech**: [ADR-0012](../decisions/0012-end-of-speech.md), proposed.
  - The cloud decides when the user has finished. The robot falls back only after a silence or 30 s, and cancels a turn in which nobody speaks.
  - Alexa's far-field devices, OpenAI's Realtime API and LiveKit Agents all leave this to the server.
  - Protocol 2.2 says so, with the same messages.
- **Listening on the robot**: [ADR-0013](../decisions/0013-listening-on-the-robot.md), proposed.
  - Wake words with microWakeWord, through pymicro-wakeword: the previous generation trained it, and Home Assistant runs it on Linux.
  - Voice with Silero VAD, through pysilero-vad.
  - Sound through PipeWire, with the voice processor as the default device, so that everything played reaches its echo canceller.
- **The `voice` module holds the conversations.**
  - Turns from the wake word; streaming; the fallbacks; answers and follow-ups; barge-in, which starts the new turn with the words that interrupted; a local cue when offline.
  - Durations are counted in bytes of audio, which add up exactly: a sum of 20 ms in floating point never reached 0.2 s.
  - It publishes the interaction state now, and behavior counts conversations as interactions.
- **New ports and adapters**: `wake_word` (`sim`, `micro`), `voice_activity` (`sim`, `silero`), and `portaudio` for the microphones and the speaker. The `pi` profile selects them.
- **Tests.**
  - The module, with fake devices.
  - The engines, on two short recordings from pymicro-wakeword and pysilero-vad (listed in `THIRD_PARTY_NOTICES.md`).
  - The PortAudio adapters, with streams that call back from a thread.
  - The module with the real engines, on a recording.

- **Decision 6, updates**: [ADR-0014](../decisions/0014-updates.md), proposed.
  - Whole images, built in CI with `rpi-image-gen`, written into the system slot that is not running and booted once on trial through the bootloader's tryboot. The new system commits itself once healthy; otherwise the next boot rolls back.
  - RAUC installs them, as in Home Assistant OS: signed bundles, streamed, and adaptive so that only changed blocks download.

**Decisions:** [ADR-0012](../decisions/0012-end-of-speech.md), [ADR-0013](../decisions/0013-listening-on-the-robot.md) and [ADR-0014](../decisions/0014-updates.md), proposed.

**Problems / unfinished:**
- The robot's own wake word waits for its name. The configuration ships `okay_nabu`, a model that comes with pymicro-wakeword.
- The mute (PRIV-1) has no control yet, and neither has the volume.
- Nothing has run on a Pi or with the voice processor. The PipeWire setup, and timings such as `end_silence` and `barge_in`, are to be checked on the robot.
- The body controller waits: the chassis' motors, encoders and driver are still unknown (hardware open issue 8), and they decide what its microcontroller must do.

**Next:** After review: the set-up protocol, which registers the robot's key; the mute and the volume; the chassis' specifications, then the body controller (ADR-0004).

## 2026-10-24 — Setting the robot up

**Done:**
- **Set-up**: [ADR-0015](../decisions/0015-set-up.md), proposed.
  - The owner's app sets the robot up over Bluetooth LE. A code on the robot's screen secures the session through SPAKE2+ (RFC 9383), the PAKE Matter uses; the messages after it are encrypted with AES-GCM.
  - The app gives the Wi-Fi network, then relays a registration that the robot signs with its TPM key, as a browser relays a security key's in WebAuthn. The robot is bound once its server accepts it, and a new owner needs a reset.
  - Compared with Matter, HomeKit, ESP-IDF, Improv, BerryLan, Reachy Mini and the device grant. The previous generation sent its PIN, the Wi-Fi password and its token in clear.
- **The protocol**, `protocol/setup/` 1.0: the Bluetooth service and its fragments, the exchange, the requests, the registration. Its example replays byte for byte, with the values an app needs to test itself.

## 2026-10-28 — Measured on the Pi 5

**Done:**
- **Today's software on the robot's Pi 5**, under Raspberry Pi OS with Python 3.13:
  - all 527 tests pass, with the C++ extension, a software TPM and a LiveKit server;
  - running, it takes 54 MB (PSS) and 0.25 % of one core.
- **ROS 2 Lyrical in Docker on the Pi**, with nine Python nodes in a ring, each publishing ten messages a second:
  - CPU: 13.6 % of one core with rclpy's `Node`, 5.5 % with `AsyncNode`, and 26 % with all nine in one process on the single-threaded executor;
  - memory: about 170 MB per process. 128 MB of it is a single region that LTTng-UST, loaded through `librcl`, makes under the 16 KB pages of Raspberry Pi OS's Pi 5 kernel.
  - With 4 KB pages, loading LTTng-UST costs 2 to 5 MB (x86, and the arm64 image emulated). Ubuntu's Raspberry Pi kernel uses 4 KB pages.
- [ADR-0017](../decisions/0017-ros-2.md) updated with these measurements: the node class is built on `AsyncNode`, the page size is one more reason for Ubuntu, and memory is estimated at roughly 50 MB per node.
- Installed on the Pi for the measurements: PortAudio, the Python headers, the TPM's libraries and swtpm, Debian's Docker, and the `ros:lyrical-ros-base` image. Everything else is in `~/ai-robot-check`.
- **The plans, checked against the Pi.** Everything that can be checked without the other parts holds:
  - Bluetooth 5.0 with LE peripheral and advertising, for set-up (ADR-0015);
  - every overlay the pin map and the parts need, in Raspberry Pi OS and in Ubuntu 26.04's Linux 7.0 kernel alike: the TPM, UART0, SPI0, I2C1, the DSI panel, the IMX500;
  - an EEPROM that boots Ubuntu 26.04, whose kernel uses 4 KB pages (ADR-0017);
  - the listening engines at 1.0 % and 2.8 % of one core (ADR-0013);
  - LiveKit's SDK on arm64 (ADR-0009);
  - room for two system slots on the 32 GB card, by estimate (ADR-0014).

  The exception is power. On Raspberry Pi's official 27 W supply, the Pi received no USB-PD offer at boot (`usbpd_power_data_objects` empty). So it assumed 3 A, and holds its USB to about 600 mA, too little for the XVF3800 at volume (hardware open issue 10). The cause is to be found: a power cycle, then the plug and cable.
- The Pi's BCM2712 is the D0 stepping.
- **Set-up over real Bluetooth.** The Pi ran the robot with the `bluez` link, and the Wi-Fi stayed simulated. A Windows PC played the owner's app, with a script built on bleak and the package's own `AppSession`. The session went:
  - through the screen protocol, it held the face, pressed "Set up with the app" and read the code, as an owner reads the screen;
  - BlueZ took the advertisement within its 31 bytes. The PC found it, with the robot's name and the service's UUID, at −80 dBm through the house;
  - the ATT MTU came to 517, so every message fit in one fragment, and the indications were confirmed;
  - SPAKE2+ and the keys took 247 ms; each request (info, networks, join, register, finish) about 28 ms;
  - a bound robot refused the registration, as it should;
  - the logs never showed the code.

  Still to try: a phone (iOS and Android) as the app, and NetworkManager joining a real network, which needs the Pi on Ethernet so that SSH survives.
- **Updates as Home Assistant OS does them**, the owner's choice: [ADR-0014](../decisions/0014-updates.md) gains decision 7.
  - GitHub Actions builds each release's image. A job that needs a maintainer's approval signs it with a key kept in a protected environment, and the release is published on GitHub Releases.
  - A channel file on GitHub Pages announces each release.
  - An `updates` node on the robot reads the channel, checks the bundle's signature and version, and installs through RAUC: when the owner says so, or by itself when idle on the charger.
  - Checked first: GitHub's downloads answer range requests, which RAUC's streaming needs; GitHub limits each file to 2 GiB, so the image has a size budget; Ubuntu's kernel has NBD and dm-verity.

## 2026-10-28 — Conversations on the robot

**Done:** [ADR-0018](../decisions/0018-conversations.md), proposed: how the voice module holds the conversations of the cloud link 3.0.
- A wake word opens a conversation, and the robot streams for all of it, its face showing that it listens.
- The cloud takes the turns. The robot ends the conversation after `nothing_heard`, `idle` or `longest`, or when its microphones go off.
- Barge-in stays the robot's own. With the voice processor's echo cancelling the robot streams while it speaks; without it, half duplex.
- Alexa listens 5 seconds after an answer and Google about 8, while Gemini Live keeps a session open. `idle` is the owner's setting, from 5 to 30 seconds.
- The owner asked for speech not meant for the robot to be told apart, rather than accepted as a cost. Alexa, Google and Gemini Live all do it:
  - the cloud judges what is said, from the start, and drops such turns, so the robot neither answers them nor stays open for them;
  - the robot adds what its camera sees once the camera is in use. It is planned, not yet in use.

**Next:** Pin ai-platform at `platform/`, and rewrite the voice and `cloud` modules for the cloud link 3.0 and set-up 2.0.
