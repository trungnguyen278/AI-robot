**Next:** Agree on ADR-0006; port the scenes (clock, weather, timers…) and status screens; on the Pi, set up the kiosk and measure.

## 2026-10-16 — Scenes on the screen

**Done:** Scenes in the renderer ([`ui/src/scenes/`](../../ui/src/scenes/index.js)): clock, weather, timer, charging and start-up. They are drawn from real data, not canned loops: the time, the weather sent by the software, a timer that counts down on the page. The face keeps its expression and watches from a corner, as in the previous generation's scene design. The screen protocol's `state` carries an optional `scene`, and `hello` a revision and the software's clock, without a new version. On the Pi side, `SceneRequest` has its own arbiter, and the `system` module shows the charging scene when the robot is plugged in. The renderer plays the start-up itself. A ten-angle review of the pull request (PR #7) found real problems, all fixed before merging. Bad scene data could freeze the face or stop the robot; it is now checked when a request is made. The face drifted between two corner scenes. The start-up had two owners. The charging scene replayed on unknown readings. Old kiosk pages never reloaded. Large static glows cost about three times a frame's drawing; they are now cached. The bundling tool built broken files silently.
**Decisions:** [ADR-0006](../decisions/0006-screen-renderer.md) refined (scenes; still Proposed).
**Problems / unfinished:** No module asks for clock, weather or timer scenes yet: that needs behaviors and a weather service. 30 of the previous library's 33 scene categories are still to port, and its network status flow.
**Next:** Agree on ADR-0006; behaviors that request expressions and scenes; on the Pi, set up the kiosk and measure.

## 2026-10-16 — First behaviors; a review checklist

**Done:** A review checklist for assistants, [`.claude/skills/review/`](../../.claude/skills/review/SKILL.md). The built-in multi-agent review costs too many tokens; this checklist runs inline and walks the classes of bugs found in PR #7. First behaviors in the `behavior` module, before the robot can talk:
- a tap on the screen pleases it, and several quick ones delight it;
- the clock takes the screen once nobody has interacted for a while, as on a smart display, until the next tap;
- the face looks sleepy from sunset, plus `sleepy_after_sunset`, until sunrise.

The times come from a new `daylight` port: `fixed` times by default, or `solar`, computed on the robot from its latitude and longitude with NOAA's equations (within a minute of an independent implementation, astral). A test follows a tap from a page through the software and back to the page.
**Decisions:** Sunrise and sunset are computed on the robot from its place, kept in `local.toml`, rather than fetched from a service. The user left that choice to me, and the `daylight` port leaves room for a service later.
**Problems / unfinished:** ADR-0006 still awaits agreement. The robot's place must be set by hand in `local.toml` (later: from the app). Taps and the time of day are the only inputs until voice and vision exist.
**Next:** The conversation flow in `behavior` once voice has a wake word; on the Pi, set up the kiosk and measure.

## 2026-10-16 — Requirements for the cloud link

**Done:** The core AI will run in the cloud (`ai-robot-server`, to be built anew rather than ported from the previous generation's server), and moods such as sleepiness probably with it. Drafted the requirements of the robot ⇄ cloud link in [`protocol/cloud/requirements.md`](../../protocol/cloud/requirements.md):
- what goes up and down;
- sessions, turns and barge-in;
- media negotiation: one side offers the codecs it supports in order of preference and the other answers, as SIP endpoints such as FreeSWITCH do (RFC 3264), with a baseline format so that it never fails;
- extensibility: the robot declares capabilities with schemas and safety classes, and the cloud calls them through one generic message, MCP-shaped, so that it can drive more of the robot without protocol changes;
- performance, reliability and working offline;
- security, checked against ETSI EN 303 645 and the OWASP IoT Top 10, and privacy;
- set-up, operations and tests.

They draw on the previous generation's protocol, xiaozhi-esp32, MCP, the Gemini Live and OpenAI realtime APIs, and Alexa Voice Service.
**Decisions:** none yet; seven are listed in its §13, each to become an ADR (transport, message format, audio, end of speech, device identity, updates, where moods live).
**Problems / unfinished:** `ai-robot-server` does not exist yet, so the requirements on the server side are for when it does. Children's data policies are to be defined before the first real users.
**Next:** Review the requirements with the user; then the ADRs of §13, starting with the transport and the message format; then a simulated cloud on the robot side (TEST-2).

## 2026-10-16 — Transport and messages of the cloud link

**Done:** The requirements of the cloud link are merged (#10). Proposed the first two of their decisions:
- [ADR-0007](../decisions/0007-cloud-link-transport.md): one WebSocket over TLS, opened by the robot. The audio is kept separable, so that WebRTC can carry it if measurements call for it. OpenAI and Pipecat recommend WebRTC for voice clients; xiaozhi, Gemini Live and the previous generation use a WebSocket.
- [ADR-0008](../decisions/0008-cloud-link-messages.md): typed JSON messages for the session; capabilities as MCP tools carried inside them, as xiaozhi does; audio in binary frames with an RTP-like header.

The requirements cited MCP 2025-06-18. The latest revision is 2026-07-28, which is stateless, with no `initialize` handshake: they now cite it, and ADR-0008 builds on it.
**Decisions:** none accepted; both ADRs are `Proposed`.
**Problems / unfinished:** Five decisions of the requirements remain: audio, end of speech, device identity, updates, moods. WebSocket against WebRTC can only be settled by measurements on the robot.
**Next:** Agree on ADR-0007 and ADR-0008. Then write the protocol in `protocol/cloud/` (schemas, header, examples), and the robot's cloud adapter with a simulated cloud (TEST-2).

## 2026-10-17 — The cloud link, version 1.0

**Done:** [Protocol 1.0](../../protocol/cloud/README.md) for the link between the robot and the cloud, with [`schema.json`](../../protocol/cloud/schema.json) and two example sessions that the tests check. On the robot:
- **The `cloud` module and port.** Two adapters: `sim`, a simulated cloud for running without a server and for tests (TEST-2), and `websocket`. The `websocket` adapter:
  - opens one connection and exchanges the hello;
  - acts as an MCP server (`server/discover`, `tools/list`, `tools/call`, `subscriptions/listen`, cancellation);
  - sends events and limits the cloud's message rate;
  - reconnects with backoff and resumes the session.
- **Capabilities.** Modules offer them on the bus with `CapabilityHost`, as EXT-9 asks. The cloud module checks the arguments against the schema, keeps out the safety classes the owner has not allowed, and times out a call that gets no answer.
- **The screen** offers `screen.show_expression`, `screen.set_mood` and `screen.show_scene`, with schemas built from its vocabulary, and the event `screen.touched`.
- **Shared code.** The JSON helpers moved to `core/data.py`, and the software's version to `ai_robot.software_version()`.
- **Checked end to end.** The robot, configured for the `websocket` adapter, worked against a small local cloud: it listed its tools, showed an expression and a scene, refused an unknown expression, and said goodbye when it stopped.

**Decisions:**
- The protocol builds on [ADR-0007](../decisions/0007-cloud-link-transport.md) and [ADR-0008](../decisions/0008-cloud-link-messages.md), still `Proposed`.
- Credentials are a bearer token from `AI_ROBOT_CLOUD_TOKEN`, provisional until decision 5.
- The cloud sees only `informational` capabilities by default.
- Invalid arguments are a tool error rather than a protocol error, as MCP advises; EXT-2 now says so.

**Problems / unfinished:**
- Turns, responses and audio frames are specified but not implemented. They wait for the voice pipeline (wake word, VAD), and until then the robot offers no audio formats.
- Renegotiating media (NEG-4) and announcing events declared after the hello are left to a later minor version.
- The `ai_backend` port of `voice` is to be replaced by turns over the link.

**Next:**
- Turns and audio on the robot, with the voice pipeline.
- More capabilities as modules gain them: gaze, motion (`physical`, off by default), timers on the robot (REL-2).
- The remaining decisions of the requirements: audio, end of speech, device identity, updates, moods.

## 2026-10-17 — Settings in one place

**Done:**
- **Tunable values moved into `software/config/base.toml`.** Every value worth tuning that sat at the top of a file now lives there, with a comment:
  - the shutdown timeout;
  - the behaviour's timings (smile, delight, taps, how often it looks at the time of day);
  - the screen's voice rate and the limits of what the cloud may ask;
  - the system's status light and charging scene;
  - the screen server's and the cloud link's timings, rates and backoff;
  - what the simulated speaker, battery, range sensor and emergency stop report.
- **No defaults left in the code.** The code takes these values as required settings, and `tests/test_registry.py` now builds every adapter from the shipped configuration, even those no profile selects yet.
- **The display name** has no fallback in the code any more; `base.toml` is its only home (ADR-0003).
- **The rule against hard-coding** is now in `AGENTS.md`, read through `CLAUDE.md`: what to tune goes in the configuration; protocol values in `protocol/`; facts named in the code with their source; one machine's values in `local.toml` or the environment.
- **A bug the audit found:** the cloud link cut a close frame's reason by bytes, which could split a UTF-8 character. It now drops the broken character.

**Decisions:** none. This applies the rule `software/README.md` already had for hardware values to every tunable value.

**Problems / unfinished:** The renderer (`ui/src/`) still holds its own values, mostly the face's design (shapes, glow), but also timings (transitions, blinks) and the low-battery threshold of 15 %. That threshold should come from the robot. Moving them needs a choice: a settings file for the renderer, or settings sent by the software in the screen protocol.

**Next:** Decide where the renderer's settings live; then turns and audio with the voice pipeline.
