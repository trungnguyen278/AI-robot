## 2026-10-15 — Raspberry Pi software skeleton

**Done:** Only the Pi 5 is fixed, so the Pi software comes first and the rest waits. Created the skeleton in [`software/`](../../software/README.md): modules talking through a message bus, hardware behind ports with simulated adapters, configuration profiles (`desktop`, `pi`), an optional C++ extension (pybind11) with Python fallbacks, tests and CI. It runs on any computer with `ai-robot --profile desktop`. Added a short product outline to the README ("What it should do") and aligned [vision.md](../vision.md) with it.
**Decisions:** [ADR-0004](../decisions/0004-pi-software-first.md) (supersedes ADR-0002); [ADR-0005](../decisions/0005-pi-software-platform.md) (Proposed).
**Problems / unfinished:** ADR-0005 awaits agreement. No real adapters yet; the AI backend interface is provisional; joint names and limits are placeholders until the arm design is fixed.
**Next:** Agree on ADR-0005; on the Pi, write the first real adapters (audio, camera, display); design the face.

## 2026-10-15 — Screen UI library

**Done:** Imported the screen UI designed in Claude Design (the previous generation's emotion library and its round-screen variant) as a new component, [`ui/`](../../ui/README.md): 82 categories, 256 variants. Removed the old product name and the personal data written into it (boot credits, Wi-Fi name, a phone owner's name); that text now comes from `ScreenData`, and every other variant still renders exactly as before. Merged the two viewers into one sheet whose screen profiles (7" 1024 × 600, 2" TFT, round 240/360/466, custom size) place the 320 × 240 stage on any display. Fixed a design bug: Babel runs every file in one global scope, and a `pulse` helper in the moon scene replaced `EmotionCore.pulse`, mistiming 20 variants (winks, yawns…). Added a smoke test and its CI. Published the sheet as a claude.ai Artifact for editing in the browser. Deleted the branch of the closed PR #2.
**Decisions:** The ESP32-S3 mentions in the hardware and firmware docs stay for now (concept v0), although the microcontroller is not chosen.
**Problems / unfinished:** How the robot shows the library (its JSX in a full-screen browser, or a port to Python) is open — see [architecture](../architecture.md#open-questions-each-should-become-an-adr); it needs a performance check on a real Pi 5. The sheet loads React and Babel from unpkg.com and compiles the JSX in the browser.
**Next:** Decide how the robot shows the library (ADR); rename the software's `face` module (proposal: `screen`) and connect it to the library.

## 2026-10-16 — Screen renderer driven by the software

**Done:** Looked at how larger robots and assistants build their screens (Anki Vector, Mycroft and OpenVoiceOS, ROS `twist_mux`, Misty, Stack-chan), and rebuilt the screen on that basis instead of carrying over the previous generation's structure, which was shaped by its microcontroller. New renderer in [`ui/`](../../ui/README.md): plain JavaScript modules, a procedural face with 14 expressions, transitions between any two, blinking, glances, breathing, gaze and voice, any screen size or shape, and a studio to try it all. New [screen protocol](../../protocol/screen/README.md). On the Pi side, the `screen` port (`sim` and `web` adapters, the latter on aiohttp) and the `screen` module (expression requests with priorities and durations) replace `display` and `face`. The previous library moved to `ui/legacy/` as the reference to port from; `protocol/` now has one folder per protocol.
**Decisions:** [ADR-0006](../decisions/0006-screen-renderer.md) (Proposed).
**Problems / unfinished:** Nothing measured on a Pi 5 yet (frame rate, CPU and memory in Chromium). No scenes or status screens ported yet. Only the conversation requests expressions; vision does not send `LookAt` yet. The robot's own voice is not measured, so the mouth makes up syllables while it speaks.
**Next:** Agree on ADR-0006; port the scenes (clock, weather, timers…) and status screens; on the Pi, set up the kiosk and measure.

## 2026-10-16 — Scenes on the screen

**Done:** Scenes in the renderer ([`ui/src/scenes/`](../../ui/src/scenes/index.js)): clock, weather, timer, charging and start-up. They are drawn from real data, not canned loops: the time, the weather sent by the software, a timer that counts down on the page. The face keeps its expression and watches from a corner, as in the previous generation's scene design. The screen protocol's `state` carries an optional `scene`, and `hello` a revision and the software's clock, without a new version. On the Pi side, `SceneRequest` has its own arbiter, and the `system` module shows the charging scene when the robot is plugged in. The renderer plays the start-up itself. A ten-angle review of the pull request (PR #7) found real problems, all fixed before merging. Bad scene data could freeze the face or stop the robot; it is now checked when a request is made. The face drifted between two corner scenes. The start-up had two owners. The charging scene replayed on unknown readings. Old kiosk pages never reloaded. Large static glows cost about three times a frame's drawing; they are now cached. The bundling tool built broken files silently.
**Decisions:** [ADR-0006](../decisions/0006-screen-renderer.md) refined (scenes; still Proposed).
**Problems / unfinished:** No module asks for clock, weather or timer scenes yet: that needs behaviors and a weather service. 30 of the previous library's 33 scene categories are still to port, and its network status flow.
**Next:** Agree on ADR-0006; behaviors that request expressions and scenes; on the Pi, set up the kiosk and measure.
